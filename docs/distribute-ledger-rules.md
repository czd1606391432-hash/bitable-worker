# 母版分发、总账、超期规则

这三项都是可选的。典型场景：一个团队有几十个项目，每个项目用一张结构相同的表，由不同的人负责；管理者想一键发表、统一看进度。

## 母版分发

### 准备

1. 做好一张**母版**多维表格：表结构、视图、自动化流程都调到满意。
2. 把母版里要处理文件的那张数据表，按普通任务表的写法写进 `config.json` 的 `tables`。
3. 在配置里声明哪张是母版：

```json
"master": {"app_token": "母版的 app_token", "link_share": "closed", "keep_rows": false}
```

| 配置项 | 含义 | 默认 |
|---|---|---|
| `link_share` | 分发出去的表的链接分享范围：`closed` 只有协作者能打开；`tenant_readable` 组织内拿到链接的人可读；`tenant_editable` 组织内拿到链接的人可编辑。对外分享一律关闭。 | `closed` |
| `keep_rows` | 是否保留母版里的行。默认会清空，这样母版里可以放示例数据。 | `false` |
| `time_zone` | 新表的时区 | `Asia/Shanghai` |

4. 建分发登记表（只做一次）：

```bash
python3 -m bitable_worker setup-registry --title 项目表分发登记
```

程序会新建一个多维表格，里面有一张「分发登记」表，并把它的所有者转给母版的所有者。

### 使用

在「分发登记」表里新增一行，填「新表名称」和「交给谁」。大约一分钟后：

- 状态变成「已分发」，「新表链接」里出现新表的链接；
- 对方收到飞书通知，成为新表的所有者；
- 新表里的任务表已经自动接入处理，不需要改配置、不需要重启。

如果失败，「说明」列会写原因；改好后把状态改回「待分发」重试。一轮最多分发 2 张，批量登记时会排队。

### 复制时程序做了什么

1. **带内容**复制母版。只复制结构的话，自动化流程和仪表盘不会带过去。
2. 清空副本里所有数据表的行（此时副本里的自动化全是停用状态，删行不会触发任何流程）。
3. 按母版此刻的开关，把副本里对应的自动化逐条启用。接口复制出来的自动化默认全部停用。
4. 设置链接分享范围。
5. 把所有者转给指定的人，应用自己保留管理权限（否则之后没法读写）。转不成的话退一步，把对方加成可管理的协作者。
6. 在副本里按**表名**找到任务表，把它登记进 `config.state.json`。

### 接入已有的表

已经在用的老表不需要复制，也可以纳入总账和规则：

1. 在老表里把应用加为文档应用（可管理）。
2. 需要处理文件的话，把它写进 `config.json` 的 `tables`。
3. 在「分发登记」表里手动加一行：填好名称和负责人，**状态直接选「已分发」**，「新表链接」填老表的链接。程序看到状态已经是「已分发」就不会去复制它，但总账会把它算进去。

### 注意

- 手动复制出来的副本是一张全新的表，不继承协作者，程序既不知道它也没有权限。要么走分发登记，要么按上面「接入已有的表」处理。
- 分发之后，母版和副本各自独立。母版后来加的列、改的自动化不会同步到已分发的表。
- 接口不能调列的顺序。想让新增的几列排在指定位置，在母版里拖好，新副本会继承。
- 副本里启用的自动化是否真的按预期运行，接口只能看到开关状态，建议第一次分发后在副本里实际触发一次确认。

## 总账

把每张已分发的表里的一张「汇总表」读出来，合并到一张总表。汇总表通常是每个项目一行，里面用公式或引用算好了各项指标。

### 配置

```json
"ledger": {
  "source_table": "项目汇总",
  "every_seconds": 300,
  "columns": [
    {"name": "项目名称", "source": "项目名称", "kind": "text"},
    {"name": "完成率", "source": "fldAbCdEf12", "kind": "percent"},
    {"name": "项目负责人", "source": "项目负责人", "kind": "user"},
    {"name": "截止日期", "source": "截止日期", "kind": "date"}
  ]
}
```

- `source_table`：每张来源表格里，汇总数据所在的数据表的名字。
- `columns[].name`：总账里的列名。
- `columns[].source`：来源表里对应的列，可以写列名或字段 ID。从同一张母版复制出来的表，字段 ID 都一样，所以写字段 ID 的话，对方改列名也不影响。
- `columns[].kind`：`text` 文本、`select` 单选、`user` 人员、`num` 数字、`percent` 百分比（进度条）、`date` 日期。
- 第一列必须是 `text`。

建总账（只做一次，建在分发登记表所在的多维表格里）：

```bash
python3 -m bitable_worker setup-ledger
```

除了你配置的列，总账还有几个内置列：来源表格（链接）、表格负责人、同步状态、同步说明、数据更新时间、来源编号（技术列，默认隐藏，不要删改）。

### 行为

- 默认每 5 分钟同步一次，刚分发了新表时立刻同步一次。内容没变的行不会重写。
- 以登记表为准：登记行删掉，总账里对应的行消失。
- 来源表被删或者程序没权限：同步状态标「表格不可用」。
- 来源表的汇总表还没填：同步状态标「未填写」。
- 飞书临时故障（网关错误、限流）时整轮跳过，不会把表误标成不可用。
- 总账里手改的内容会被下一次同步覆盖。想加备注，另建一张表引用它。

## 超期规则

某一列停在某个值超过 N 天的行，自动改成别的值。

```json
"rules": [
  {
    "name": "待筛选超过7天自动淘汰",
    "enabled": true,
    "tables": ["master", "distributed"],
    "table": "候选人",
    "when": {"field": "当前环节", "is": "待筛选"},
    "date_field": "推荐日期",
    "older_than_days": 7,
    "set": {"当前环节": "淘汰"},
    "set_if_empty": {"淘汰原因": "超过7天未进入面试，系统自动淘汰"},
    "every_seconds": 300
  }
]
```

| 配置项 | 含义 |
|---|---|
| `tables` | 规则作用于哪些多维表格。可以写 `"all"`（所有接入的表）、`"master"`（母版）、`"distributed"`（程序分发出去的表）、具体的 app_token，或者它们的列表。 |
| `table` | 多维表格里的哪张数据表，写表名或 table_id。不写就用该多维表格里的任务表。 |
| `when` | 条件：`field` 这一列的值等于 `is`。 |
| `date_field` | 从哪一天开始算。这一列没填、或者没配这一项，就按这一行的创建时间算。 |
| `older_than_days` | 超过多少天。 |
| `set` | 命中的行改成什么。 |
| `set_if_empty` | 只有当这些列为空时才填，不覆盖人写的内容。列不存在就忽略。 |
| `enabled` | 写 `false` 可以临时关掉。 |

**启用前先试算。** 规则会直接改数据，而且老表里往往积压了很多早就超期的行，一开就会全部命中：

```bash
python3 -m bitable_worker rules-dry
```

它只统计每条规则在每张表里会改多少行，不改任何数据。数字符合预期再启动常驻进程。

用 `["master", "distributed"]` 这种写法，以后新分发的表会自动适用规则，不用再改配置。
